# AI 护栏规则

> 本文档定义 AI 的行为边界，AI 必须严格遵守。

---

## 核心原则

**AI 只做被明确要求的事情，不做任何假设或预设。**

---

## 🚨 会话启动检查（强制）

> **每次新会话开始时，AI 必须先执行此检查，再进行任何实现工作。**

### 必读文档清单

在开始任何编码任务之前，AI **必须**先阅读以下文档：

| 文档 | 路径 | 包含信息 |
|------|------|----------|
| 系统架构 | `spec/architecture.md` | Unity 版本、渲染管线、技术栈 |
| 编码规范 | `spec/coding-standards.md` | 代码风格、命名规范 |
| 本文档 | `spec/ai-guardrails.md` | AI 行为边界 |

### 技术栈速查

| 项目 | 值 | 影响 |
|------|-----|------|
| 引擎 | Unity 6.3 LTS | 使用新 Input System |
| 渲染管线 | URP | Shader 需兼容 URP |

## 📋 功能开发流程（强制）

```
Step 1: 需求分析
    ↓
    AI 将需求整理到 spec/features/xxx.md
    ↓
Step 2: 用户确认设计
    ↓
    用户明确说"确认"后才能继续
    ↓
Step 3: AI 生成代码
    ↓
    代码中包含调试日志（Debug.Log）
    ↓
Step 4: AI 自检
    ↓
    检查：编译错误、组件挂载、引用设置
    ↓
Step 5: 输出测试结论
    ↓
    明确说明：是否需要用户测试？如需，给出测试步骤
    ↓
Step 6: 用户测试（如需）
    ↓
    用户只需看 Console 输出 + 简单操作
    ↓
Step 7: 反馈与修复
    ↓
    有问题 → AI 修复 → 循环
    ↓
Step 8: 功能确认
    ↓
    AI 删除调试日志（或改为条件编译）
    ↓
Step 9: AI 提交 Git
```

### 自检内容

| 检查项 | 方法 |
|--------|------|
| 编译错误 | 读取 Unity Console |
| 组件挂载 | 通过 MCP 检查 GameObject 组件列表 |
| 引用设置 | 通过 MCP 检查组件属性 |
| 预制体 | 确认预制体存在且配置正确 |

### 测试结论格式

```
## 自检结果

| 检查项 | 状态 |
|--------|------|
| 编译 | ✅/❌ |
| 组件 | ✅/❌ |
| 引用 | ✅/❌ |

## 是否需要用户测试

[是/否] - [原因]

## 测试步骤（如需）

1. [具体操作]
2. [预期结果]
3. [如何判断成功/失败]
```

## ✅ AI 可以做的事情

| 允许 | 条件 |
|------|------|
| 创建/修改代码 | 用户明确要求，且有 spec 文档支撑 |
| 创建 CSV 数据表 | 用户确认了数据结构设计后 |
| 创建新的 spec 文档 | 用户要求定义某个系统/规范时 |
| 修复 Bug | 用户指出问题并要求修复 |
| 重构代码 | 用户明确要求重构 |
| 生成目录结构 | 仅创建空目录占位，不预填内容 |

---

## ❌ AI 禁止做的事情

| 禁止 | 原因 |
|------|------|
| 预设游戏玩法设计 | 玩法需用户主导设计 |
| 假设数据表结构 | 数据结构需用户确认 |
| 自行添加示例数据 | 示例数据容易误导 |
| 引入未讨论的系统 | 如擅自创建"技能系统"、"房间系统" |
| 预设枚举值/常量 | 如 SkillType.Melee 等具体值 |
| 做"好玩/难易度"评价 | 用户明确不需要 |
| 跳过用户确认直接开发 | 必须等用户明确说"确认" |

---

## 边界划分

### 基础框架（AI 可自行创建）

- 单例基类/模式
- 事件中心（通用结构）
- 文件目录结构（空目录）
- .gitignore
- 代码规范文档
- Git 工作流文档

### 业务设计（需用户确认）

- 具体 Manager 的实现
- 数据表结构（CSV schema）
- 枚举定义
- 游戏数值
- 具体玩法逻辑

---

## 违规处理

如果 AI 违反了上述规则：

1. 用户指出问题
2. AI 立即删除/撤销相关内容
3. AI 回到正确的工作流程
